# Аналіз лабораторної 3: CQS

## Що змінилося в структурі порівняно з лабою 2
- Файл `application/use_cases.py` (14 класів «Use Case», де читання і запис жили разом) розділився на два підпакети:
  - `application/commands/` (`users.py`, `movies.py`, `reports.py`) — 7 команд (`RegisterUserCommand`, `CreateMovieCommand`, `UpdateMovieCommand`, `DeleteMovieCommand`, `AddReportCommand`, `UpdateReportCommand`, `DeleteReportCommand`) і 7 `*Handler`;
  - `application/queries/` — 7 запитів (`ListMoviesQuery`, `GetMovieQuery`, `ListReportsQuery`, `GetMovieSummaryQuery`, `GetTopMoviesQuery`, `GetRegionRevenueQuery`, `LoginQuery`), їхні `*QueryHandler`, Read Models (`read_models.py`) та порти читання (`ports.py`).
- Доменні репозиторії (`domain/repositories.py`) стали «write-only»: зникли `list`, `list_for_movie`, `totals_by_movie`, `revenue_by_region`. З домену видалено `services.py` (`summarize`, `roi`) — аналітика більше не рахується в Python.
- З'явився другий набір адаптерів `infrastructure/read_repositories.py` — SQL напряму в БД, без мапінгу в доменні сутності.
- Контролери в `presentation/routers.py` лише мапають HTTP → Command/Query і викликають `handler.handle(...)`. Окремих схем відповідей у `presentation/schemas.py` більше немає: запити повертають Read Models.
- Змінився HTTP-контракт команд: `POST` повертає тільки `{"id": ...}`, `PUT` — `204` без тіла; створений/оновлений ресурс клієнт отримує окремим `GET`.

## Переваги CQS
- **Прозоре розділення відповідальності.** `UpdateMovieHandler` знає лише про `Movie`, фабрику і репозиторій запису; про агрегати чи форму відповіді в ньому нічого немає. У лабі 2 `GetTopMovies` та `CreateMovie` лежали в одному модулі і мали спільні залежності.
- **Швидші запити.** `GetTopMovies` у лабі 2 робив `totals_by_movie` + `movies.get()` для кожного фільму (N+1), а `GetMovieSummary` вантажив усі звіти в пам'ять. Тепер `SqlAnalyticsReadRepository.top_movies` — один `JOIN + GROUP BY`, `movie_summary` — дві агрегації на стороні БД. Доменні об'єкти й мапери для читання не створюються.
- **Різні стратегії тестування.** Команди тестуються unit-тестами на fake-репозиторіях (11 тестів у `tests/application` + 24 в `tests/domain`), запити — інтеграційними тестами з реальною БД і даними, підготовленими `seeded` напряму в таблиці (10 тестів у `test_queries_api.py`). Команди перевіряють поведінку (зайнятий слот → `ConflictError`, невалідний запис не доходить до репозиторію), запити — результат (SQL, `LEFT JOIN`, фільтри, поля Read Model).
- **Оптимізація без ризику для домену.** Можна змінити SQL або додати індекс, не торкаючись інваріантів.

## Недоліки CQS
- **Ще більше класів і файлів.** Кожна операція — пара «Command + Handler» або «Query + Handler». Для простих `GetRegionRevenueQuery` це пара класів заради одного виклику репозиторію (`GetRegionRevenueQueryHandler` лише делегує).
- **Дві моделі даних.** Щоб додати поле до фільму, треба змінити доменну сутність, ORM-модель, мапер для запису **і** read model із SQL для читання.
- **Клієнту потрібен другий запит.** Після `POST /movies` клієнт отримує тільки id і для даних мусить викликати `GET /movies/{id}`.
- **Два набори портів і адаптерів**, а тести команд та запитів використовують різні інструменти (fakes проти реальної БД) — більше підтримки.
- **Узгодженість.** У межах однієї БД проблем немає, але якщо читання колись підуть у репліку, виникне eventual consistency; архітектура до цього вже готова, проте це додаткова складність.

## Чим Command/Query Handler відрізняється від Service, що робить усе сам
У лабі 2 один клас (напр. `AddReport`/`ListReports` у спільному модулі) міг одночасно читати, змінювати стан і повертати доменну сутність. Тепер Handler має **одну** причину для зміни і **одну** сигнатуру: `handle(command) -> id | None` або `handle(query) -> ReadModel`. Handler не отримує «все підряд» (`reports`, `movies`, `analytics`), а лише ті порти, що потрібні його операції: `AddReportHandler(movies, reports, factory)`, `GetMovieSummaryQueryHandler(analytics)`. Сервіс-комбайн накопичує залежності й методи, а контролер залежить від всього сервісу; Handler — крихітний, його легко замінити, декорувати (транзакція, логування, кеш) і тестувати окремо.

## Вплив на розширюваність
- **Нова команда** (скажімо, `ArchiveMovieCommand`): додається новий клас-команда, новий handler, один рядок у `Handlers` і `bootstrap.py`, один ендпоінт. Існуючі handler-и й тести не змінюються — діє Open/Closed.
- **Зміна існуючого сервісу** (лаба 2): довелося б відкривати `use_cases.py`, де змінюється клас, що живе поряд з іншими, і ризикувати зачепити читання.
- **Нове читання** (напр., «збори за місяць») — лише новий Query + read-репозиторій; доменний код і запис не змінюються взагалі, а SQL можна оптимізувати окремо.
Обмеження: додавання поля у сутність усе одно зачіпає обидві сторони (див. недоліки).

## Чи відрізняється структура даних Query від доменної моделі
Так, і суттєво:
- `MovieListItem` має `total_revenue_usd` — агрегат зі звітів; у домені `Movie` про збори нічого не знає (це інший агрегат).
- `ReportItem.avg_ticket_price_usd` обчислюється в SQL/мапінгу, у `BoxOfficeReport` такого поля немає.
- Read Models — плоскі `int`/`str`/`date`, без Value Objects (`Money`, `RegionCode`) і без поведінки; доменна `Movie` має `budget: Money` і методи `update`, `ensure_accepts_report_for`.
- `MovieSummary` і `TopMovieItem` — це проєкції для екрана аналітики, які не відповідають жодній сутності.
**Чому це важливо:** (1) API-контракт не залежить від внутрішніх змін домену — можна перейменувати поле в сутності й не зламати клієнтів; (2) домен не роздувається полями «для відображення» й залишається захищеним від порушень інваріантів; (3) читання не платить за завантаження агрегатів і мапінг; (4) жоден клієнт не отримує змогу мутувати доменний об'єкт, який випадково «витік» у відповідь.
